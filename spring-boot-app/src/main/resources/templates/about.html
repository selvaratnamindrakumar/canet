Spring Boot vs JavaScript-based HTTPS Data Fetching

Detailed comparison

Concern JavaScript (browser fetch / Node proxy) This system (Spring Boot + Thymeleaf)
HTTPS & CORS Browser enforces CORS on every cross-origin HTTPS call. Requires the remote API to set Access-Control-Allow-Origin, or you must add a proxy server anyway — adding a layer of complexity. The JVM makes the HTTPS request server-to-server. CORS does not apply. No proxy needed. SSL is handled by Java's trust store, which already trusts all major CAs.
API key / credential safety Any API key embedded in client-side JS is visible in browser DevTools and can be scraped from the bundle. Credentials live in application.yml or environment variables on the server — never sent to the browser.
Dependency surface A typical React/Vue project pulls in 500 – 1 500+ transitive npm packages. Each is a potential vulnerability and a maintenance burden (npm audit warnings, breaking changes, abandoned packages). Four Maven dependencies: spring-boot-starter-web, thymeleaf, actuator, and spring-boot-starter-test. Spring Boot manages compatible versions via its BOM.
Build toolchain Requires Node.js, npm/yarn/pnpm, a bundler (Webpack / Vite / esbuild), Babel or tsc, and often ESLint + Prettier. Breakage when Node versions or bundler configs diverge across machines. mvn package — one command, reproducible on any machine with Java 17. No separate frontend build step.
Docker image size A Node-based image typically includes the Node runtime and may contain node_modules unless carefully pruned. Images of 400 MB+ are common. Multi-stage build: the Maven stage is discarded. The final image is eclipse-temurin:17-jre-alpine plus the single fat JAR — typically ~180 MB.
Type safety JavaScript is dynamically typed. A shape change in the remote JSON silently produces undefined values that only surface as runtime errors in the UI. DataItem is a typed Java class. @JsonIgnoreProperties(ignoreUnknown = true) handles extra fields gracefully; missing required fields cause a clear deserialization error, not a silent UI glitch.
Error handling Errors must be handled in both the browser fetch layer (network, CORS, HTTP status) and in the UI rendering layer — two separate error boundaries in different files. A single try/catch in HttpsDataServiceImpl covers all failure modes. The controller always passes a (possibly empty) list to the template, which shows a clear warning.
Testing the HTTPS call Mocking fetch or axios in Jest requires manual stubs or libraries like msw (Mock Service Worker). Testing real SSL handshakes from the browser is impractical in unit tests. Three complementary layers:
  1. MockMvc — controller slice, zero network
  2. MockRestServiceServer — built into Spring, intercepts RestTemplate at the JVM level
  3. WireMock — embedded HTTP server testing real TCP, delays, 5xx, and request verification
Server-side rendering (SEO) Single-page apps deliver an empty <div> until JS loads and the fetch completes. Requires SSR frameworks (Next.js, Nuxt) to fix — adding yet more complexity. Thymeleaf renders the full HTML on the server before the first byte reaches the browser. Works without JavaScript enabled. Fully crawlable by search engines with no extra configuration.
Operational observability Requires third-party APM agents or custom logging to observe outbound HTTP calls. Browser network logs are client-only. spring-boot-starter-actuator provides /actuator/health and /actuator/info out of the box. SLF4J logs every outbound call with URL and error detail, visible in any log aggregation tool.
Long-term maintainability JavaScript ecosystem moves fast. A project untouched for 12 months can accumulate dozens of breaking changes and security advisories across its transitive dependency tree. Spring Boot's LTS releases and BOM mean a single version bump (<parent> in pom.xml) updates all compatible dependencies in one step. Java LTS versions provide multi-year stability guarantees.

When a JavaScript frontend is still the right choice

This comparison is not a blanket rejection of JavaScript. A client-side JS approach is preferable when:

  • The UI requires rich, stateful interactivity (drag-and-drop, real-time collaboration, canvas/WebGL).
  • The application is a public consumer SPA where time-to-interactive and offline capability are critical.
  • The team's existing expertise is primarily in a JS framework and the switch cost outweighs the benefits.
  • The remote API is already under your control and CORS headers can be set correctly.

For the CaNet use-case — fetching structured JSON from a third-party HTTPS endpoint and displaying it in a table — the Spring Boot approach eliminates an entire category of infrastructure complexity with no meaningful trade-off.
